# MCP Use Cases

Практические сценарии, где **MCP + AI-агенты** помогают автоматизировать рутинные задачи.

> Репозиторий отвечает на вопрос: **«Я понял MCP и безопасность. Что можно попробовать построить самому?»**

## Три сценария

### 1. Vulnerability Analysis

```text
Объект → данные → анализ → обоснование → человек принимает решение
```

Агент собирает разрешённый контекст об уязвимостях и версиях и готовит рекомендации. Финальное решение остаётся за инженером.

Папка: [`use_cases/cve_analysis`](use_cases/cve_analysis)

### 2. API Agent

```text
Задача → разрешённый API → обработка → результат
```

Пример работы с внешним сервисом через ограниченный набор разрешённых методов и адресов.

Папка: [`use_cases/api_agent`](use_cases/api_agent)

### 3. Files & Report Agent

```text
Файлы → извлечение данных → обработка → отчёт
```

Агент работает только с разрешённой директорией и сохраняет результат в выделенную область.

Папка: [`use_cases/files_report`](use_cases/files_report)

## End-to-end: локальная LLM + MCP

В репозитории есть воспроизводимый агентный сценарий `llm_agent_demo.py`:

```text
USER
  ↓
Qwen3 1.7B / Ollama
  ↓
MCP tool discovery
  ↓
LLM выбирает find_cves
  ↓
MCP Server
  ↓
structured CVE data
  ↓
LLM формирует ответ
```

Запуск:

```bash
ollama pull qwen3:1.7b
python llm_agent_demo.py
```

Демо использует локальные учебные CVE из `use_cases/cve_analysis/data/cves.json`; LLM не является источником фактов об уязвимостях.

## Общий принцип

Сценарий меняется, но базовая схема остаётся той же:

```text
USER
  ↓
AGENT
  ↓
POLICY / VALIDATION
  ↓
TOOL
  ↓
RESULT
  ↓
HUMAN — когда решение требует ответственности или дополнительной проверки
```

Агент может **собирать контекст, анализировать и готовить обоснование**. Там, где действие имеет существенные последствия, граница ответственности остаётся у человека.

## Как использовать идеи

Не обязательно копировать конкретный пример. Полезнее забрать паттерн:

```text
задача → контекст → инструменты → ограничения → результат → контроль
```

Его можно адаптировать для анализа уязвимостей, работы с API, обработки документов, подготовки отчётов и других сценариев.

## А если задача становится сложнее?

Один агент не обязан превращаться в набор subagents.

**Subagents — один из вариантов декомпозиции сложной задачи**, когда отдельные части действительно полезно разделить между специализированными агентами. Для простого сценария одного агента часто достаточно.

## Куда развивается подход

Условно путь можно представить так:

```text
AI-помощник
    ↓
полуавтономный агент
    ↓
автономные действия под контролем
```

Чем выше автономность, тем важнее технические границы: permissions, policy enforcement, sandbox, HITL, audit и наблюдаемость.

## Важно

Все примеры учебные. Mock/local data используются там, где это позволяет запускать сценарий без ключей, токенов и доступа к реальным системам. Это **деталь демо, а не архитектурное требование**.

Репозиторий не описывает внутренние системы, архитектуру или процессы какой-либо организации.

Перед production-использованием потребуются собственная модель угроз, IAM, управление секретами, rate limits, аудит, наблюдаемость и отдельный policy enforcement layer.
